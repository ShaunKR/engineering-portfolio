# [doc] PR과 코드 리뷰

> 팀에서 검토할 제안 기준과 복사해서 사용할 양식이다.

## 작성 기준

변경의 목적과 판단 근거를 리뷰어가 이해할 수 있게 작성한다. 목적이 다른 변경은 나누고, 함께 바뀌어야 하는 구현·테스트·설정은 같은 맥락에서 설명한다. 파일 수에 일률적인 제한을 두기보다 검토 가능한 범위인지 판단한다.

## PR 작성 양식

```markdown
## 문제와 변경
- 어떤 문제를 해결하는가?
- 호출자 또는 운영 동작이 어떻게 달라지는가?

## 설계 판단
- 검토한 대안과 선택 이유:
- 영향받는 API, 데이터, 의존 서비스:

## 검증
- 실행한 검사와 결과:
- 재현 방법 또는 공개 가능한 로그:
- 수행하지 못한 검증과 이유:

## 배포와 복구
- 설정 변경 및 적용 순서:
- 되돌리는 방법과 데이터 제약:

## 관련 기록
- 이슈 또는 ADR:
```

## 리뷰 우선순위

1. 요구사항과 실패 조건에 맞게 동작하는지 확인한다.
2. 데이터 변경, 접근 제어, 재시도·중복 처리 등 영향 범위를 살핀다.
3. 테스트가 실제 위험을 검증하는지 확인한다.
4. 책임 경계와 유지보수성을 검토한다.
5. 자동 도구로 처리할 수 없는 가독성 문제를 확인한다.

## 의견 처리

`필수 수정`, `질문`, `제안`을 구분한다. 필수 수정에는 실패 조건과 근거를 적는다. 선호가 다른 경우에는 기존 합의와 적용 비용을 비교한다. 결정이 오래 남아야 하면 [ADR](설계의사결정.md)로 연결한다.

개발 PL이 모든 변경의 단일 승인자가 되기보다 영역별 리뷰 책임을 분산한다. 대기 PR은 팀이 확인하고 일정에 영향을 주는 의존성을 조기에 공유한다.
