# [doc] 코드 컨벤션

> 팀에서 검토할 제안 기준이다. 과거 조직의 실제 규정 원본이 아니다.

## 목적과 적용 범위

코드 스타일 논쟁을 줄이고, 변경 의도와 실패 동작을 리뷰할 수 있도록 한다. 언어별 스타일은 저장소의 기존 규칙을 우선하며 Java, C#, Bash에 동일한 표기법을 강제하지 않는다.

## 제안 규칙

| 항목 | 기준 | 이유 |
| --- | --- | --- |
| 명명 | 업무 용어와 역할을 드러내고 모호한 약어를 피한다 | 같은 개념을 같은 이름으로 이해하기 위해 |
| 함수와 모듈 | 변경 이유가 다른 책임은 분리한다 | 수정 영향 범위를 판단하기 위해 |
| 예외 | 실패를 숨기지 않고 호출자에게 필요한 의미를 전달한다 | 정상·실패 흐름을 구분하기 위해 |
| 로그 | 사건, 결과, 추적 식별자를 기록한다 | 장애 흐름을 연결하기 위해 |
| 설정 | 비밀 값과 환경별 주소는 코드에 넣지 않는다 | 노출과 환경 간 혼용을 방지하기 위해 |
| 변경 범위 | 기능 수정과 대규모 포맷 변경은 분리한다 | 실제 동작 변경을 읽기 쉽게 하기 위해 |
| 주석 | 코드로 드러나지 않는 선택 이유와 제약을 설명한다 | 코드와 중복되는 설명을 줄이기 위해 |

로그에는 비밀번호, 토큰, 원문 개인정보를 남기지 않는다. 추적 식별자도 인증 수단으로 사용하지 않는다.

## 언어별 합의

| 환경 | 합의할 내용 |
| --- | --- |
| Java / Spring Boot | 패키지 경계, 클래스·메서드 명명, 예외 변환 위치, 포맷터 |
| C# / .NET | 네임스페이스와 명명, 비동기 메서드 표기, nullable 정책, 포맷터 |
| Bash | 인자 검증, 변수 인용, 오류 처리, 명령 실패 시 복구 범위 |

도구와 버전은 실제 저장소에 맞춰 고정한다. 도구 도입 전에는 기존 코드에 미치는 변경량을 검토한다.

## 자동 검사와 예외

자동화 가능한 포맷·정적 검사는 CI로 옮기고, 리뷰는 동작과 설계에 집중한다. 이 저장소에는 본 문서만으로 CI 검사가 활성화되지 않는다.

기존 코드의 위반을 한꺼번에 고치기 어려우면 새 변경부터 적용한다. 예외에는 사유, 영향, 담당자와 재검토 시점을 기록한다.
