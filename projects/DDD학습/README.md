# [study] 물류 대시보드 코드로 살펴본 DDD

직접 작업한 물류 통합 대시보드의 Java 백엔드를 기준으로 DDD의 업무 경계, 계층별 책임과 도메인 규칙 분리를 공부한 기록이다. 실제 코드에서 확인한 구조와 앞으로 적용할 수 있는 설계를 구분한다.

## 학습 자료

- [실제 코드 구조 분석](실제코드구조분석.md): 업무별 패키지, 조회 흐름, 서비스와 데이터 접근 책임
- [도메인 모델링 개선안](도메인모델링개선안.md): 순수 정책 분리, 외부 데이터 변환 경계와 검증 기준

## 코드 확인 범위

- 확인일: 2026-10-25
- 기준: 기존 대시보드 작업 채팅에서 사용하던 Mac 로컬 Git 작업본
- 기준 커밋: `c82a9d1ca797fc302bd1270b927c6f80f4262710`
- 분석에 사용한 Java 파일 8개는 위 커밋의 파일과 내용이 일치함을 확인했다.
- 현재 GitHub 연결 계정에서는 원격 저장소에 접근되지 않아 원격 브랜치 최신 상태와의 일치는 확인하지 못했다.

고객사 원본 소스, SQL, 접속 설정, 장비별 코드와 운영 수치는 복사하지 않았다. 이 자료는 코드 분석과 설계 제안이며, 원본 프로젝트에 리팩터링을 적용하거나 운영 효과를 검증한 결과가 아니다.

## 핵심 관찰

| 확인한 내용 | DDD 관점의 해석 |
| --- | --- |
| 업무별 패키지 아래 controller/service/repository/dto 배치 | 업무 경계를 검토할 출발점 |
| 서비스에서 시간에 따른 유효성 판단 | 도메인 정책을 분리할 수 있는 후보 |
| Repository에서 조회와 DTO 매핑 | 조회 데이터 접근 구현 |
| 다른 업무 영역의 캐시를 직접 참조 | 영역 간 의존성과 데이터 계약을 검토할 지점 |
| enum으로 업무 분류 코드 변환 | 코드 값과 의미를 연결한 모델링 요소 |

Controller–Service–Repository 구조와 `domain` 폴더만으로 DDD 전체를 적용했다고 판단하지 않는다. 애그리거트의 상태 변경·불변식, 도메인 이벤트와 경계별 모델을 이 코드 분석에서 확인했다고 주장하지 않는다.
