# DDD 관점의 도메인 모델링 개선안

아래 설계는 실제 코드 분석 후 작성한 학습용 제안이다. 원본 프로젝트의 현재 구현이나 적용 완료 상태를 나타내지 않는다.

## 1. 먼저 분리할 규칙

반송 상태 표시에서 시간 유효성을 판단하는 규칙을 먼저 분리하는 접근을 검토한다. 업무 규칙과 화면 표시 정책 중 어느 쪽인지 현업 요구사항을 확인한 뒤 이름과 소유 영역을 정한다.

```text
현재 서비스의 역할
조회 → 현재 시각 읽기 → 유효성 판단 → DTO 변환 → 캐시 교체

제안하는 분리
응용 서비스: 조회 결과, 현재 시각과 설정을 준비하고 흐름 조율
정책: 입력 값과 시각으로 유효 여부만 판단
조회 어댑터: 외부 데이터 조회와 내부 입력 모델 변환
캐시: 완성된 응답의 보관과 교체
```

제안 정책에는 DB, Spring 어노테이션, 스케줄러와 직접적인 현재 시각 조회를 넣지 않는다. 유효 기간과 현재 시각을 입력으로 받게 해 경계 조건을 확인하기 쉽게 한다. 성능이나 유지보수성이 실제로 개선됐다는 결과는 아직 없다.

## 2. 검증할 경계 조건

확인한 기존 규칙은 “발생 시각 + 유효 기간이 현재보다 뒤인 경우 유효”라는 형태다. 정확한 운영 임계값은 공개하지 않는다.

| 입력 상황 | 기존 코드에서 읽은 판단 또는 확인할 내용 |
| --- | --- |
| 식별 값 없음 | 표시할 값 없음 |
| 발생 시각 없음 | 표시할 값 없음 |
| 만료 시각이 현재보다 뒤 | 유효 |
| 만료 시각과 현재가 같음 | 유효하지 않음 |
| 만료 시각이 현재보다 앞 | 유효하지 않음 |
| 미래의 발생 시각 | 현업에서 허용하는지 확인 필요 |
| 유효 기간이 0 또는 음수 | 설정 검증을 둘지 확인 필요 |

표는 코드 해석과 후속 테스트 명세다. 이번 작업에서 자동화 테스트를 구현·실행한 결과는 아니다.

## 3. 외부 데이터의 의미를 변환하는 경계

기존 시스템의 코드 값과 테이블 구조를 새 모델 전체에 그대로 전파하지 않는 방안을 검토한다. 조회 어댑터가 외부 값을 의미 있는 내부 입력으로 바꾸고, 지원하지 않는 값이나 조회 실패의 처리를 명시한다.

```mermaid
flowchart LR
    External[외부 시스템 조회 결과] --> Adapter[조회·변환 어댑터]
    Adapter --> Model[내부 입력 모델]
    Model --> Policy[유효성 정책]
    Policy --> App[응용 서비스]
    App --> View[조회 응답]
```

현재 enum 변환만으로 완성된 Anti-Corruption Layer가 있다고 주장하지 않는다. 외부 모델과 내부 모델의 의미 차이를 확인하고 필요한 변환 책임부터 정의한다.

## 4. 조회 모델과 도메인 모델

이 대시보드는 조회와 화면 집계가 중심이다. 단순한 조회까지 모두 Entity·Aggregate로 바꿀 필요가 있는지는 별도로 판단한다.

- 조회 DTO: 화면이 요구하는 데이터 표현에 사용한다.
- Value Object 후보: 단위, 유효 범위와 값 동등성이 의미 있는 개념에 한해 검토한다.
- Entity 후보: 정체성과 생명주기가 실제 요구사항에 있는 경우 검토한다.
- Aggregate 후보: 함께 지켜야 할 불변식과 상태 변경의 일관성 경계가 있을 때 정의한다.

식별자 필드가 있는 DTO를 Entity라고 부르거나, 조회 결과 목록을 Aggregate라고 부르는 것만으로 설계가 달라지지는 않는다. 현재 코드에 명령·조회 모델이 완전히 분리된 CQRS가 적용됐다고도 주장하지 않는다.

## 5. 영역 간 데이터 계약

다른 영역의 캐시 클래스를 직접 참조하는 부분은 소비자가 필요한 최소한의 조회 계약으로 바꿀지 검토한다. 인터페이스 추가만으로 Bounded Context가 확립되지는 않으며 용어·소유권·오류 상태를 함께 합의해야 한다.

예를 들어 “조회할 수 없음”, “조회 결과가 비어 있음”, “정상 값이 0”을 구분해야 하는지 검토한다. 기존 fallback을 바꾸면 화면 동작도 달라질 수 있으므로 독립적인 요구사항과 검증이 필요하다.

## 6. 적용 순서 제안

1. 기존 코드의 유효성 판단을 경계 조건 테스트로 고정한다.
2. 시간 규칙만 순수 정책으로 분리하고 기존 응답이 유지되는지 확인한다.
3. 외부 데이터 변환과 미지원 값 처리를 정리한다.
4. 영역 간 조회 계약과 데이터 소유권을 정리한다.
5. 별도 요구가 확인될 때 상태 변경 모델과 서비스 분리를 검토한다.

전체 패키지 재편이나 MSA 전환을 먼저 수행하는 개선안은 아니다. 이 문서의 변경은 원본 소스에 적용하지 않았다.
