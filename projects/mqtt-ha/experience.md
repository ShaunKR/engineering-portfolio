# MQTT 브로커 전환 및 공유 구독 테스트

## 배경

기존 Mosquitto 기반 환경에서 EMQX 5.0을 사용하는 구성으로 변경하면서, 브로커 장애에 대비한 전환 방식과 공유 구독(Shared Subscription)을 테스트했다. Docker Compose로 테스트 환경을 구성했다.

## 구성과 변경 결과

- EMQX 5.0 브로커를 각각 독립적으로 구성했다.
- 브로커 앞에 HAProxy를 두고, 애플리케이션은 VIP를 통해 접속하도록 구성했다.
- Keepalived를 이용한 VIP 전환 방식을 적용했다.
- 애플리케이션의 접속 주소를 변경하지 않고 장애 상황에 대응하는 구성을 테스트했다.
- 공유 구독을 적용하고, 백업 브로커 쪽에서 구독 중인 토픽이 처리되지 않도록 제어하는 동작을 함께 테스트했다.

최종적으로 Keepalived를 사용하는 VIP 기반 전환 방식으로 변경했다.

## 대비하려던 이슈

| 이슈 | 테스트 및 적용 내용 |
| --- | --- |
| 장애 시 애플리케이션의 브로커 접속 주소 변경 필요 | VIP를 단일 접속 주소로 사용 |
| 접속 경로 장애에 대한 전환 필요 | Keepalived 기반 VIP 전환 방식 적용 |
| 브로커 장애 시 백업 경로로 전환 필요 | HAProxy와 독립 브로커 구성에서 전환 동작 테스트 |
| 여러 구독자의 메시지 처리 분담 필요 | EMQX 5.0 공유 구독 테스트 |
| 백업 쪽에서 의도하지 않은 메시지 처리 발생 가능성 | 백업 브로커 쪽 토픽 처리를 제한하는 동작 테스트 |

## 당시 확인 방법

당시 기억으로는 EMQX 관리 콘솔에서 각 브로커의 접속 클라이언트 수 변화를 확인하고, 클라이언트가 백업 브로커 쪽으로 재연결되었는지를 판단했다. 콘솔에 표시되는 연결 수를 기준으로 전환 여부를 확인한 수동 테스트였다.

현재 콘솔 캡처와 당시 수치가 남아 있지 않아 구체적인 연결 수와 전환 시간은 기록하지 않는다. 이 확인 방법만으로 메시지 유실·중복 여부, 구독 복구 또는 업무 처리의 연속성까지 검증했다고 판단하지 않는다.

## 기록 범위

과거 수행한 테스트와 구성 변경 경험을 정리한 문서다. 당시 Compose 파일과 설정, 테스트 로그는 현재 보관되어 있지 않다.

HAProxy의 `backup` 지정 여부, VIP 전환과 브로커 선택의 구체적인 연동 설정, 백업 쪽 메시지 처리 제한의 구현 방식은 확인되지 않았다. 전환 시간, 메시지 유실·중복 여부 및 세션 유지에 관한 정량 결과는 기재하지 않는다.
