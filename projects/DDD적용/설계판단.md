# 설계 판단과 DDD 적용 범위

## 업무 경계를 먼저 정리한 이유

센터 내 여러 설비는 데이터 형식뿐 아니라 같은 상태 표현의 의미도 다를 수 있다. 단일 시스템을 위해 만든 구조를 그대로 확장하면 여러 업무의 분기와 조회 처리가 한곳에 모이기 쉽다.

따라서 설비 현황을 업무 도메인별로 나누고 각 영역에서 사용하는 용어, 데이터 조회와 상태 해석 책임을 정리하는 데 DDD를 적용했다.

## 적용의 중심

| 판단 | 설계에 반영한 내용 |
| --- | --- |
| 업무별 변경을 구분 | 기능을 업무 도메인별 패키지에 배치 |
| 요청과 업무 처리를 구분 | Controller는 요청 수신, Service는 처리 흐름과 응답 조합 담당 |
| 외부 데이터 접근을 구분 | Repository에서 조회와 결과 매핑 담당 |
| 업무 코드의 의미 표현 | enum으로 분류 코드와 의미 연결 |
| 통합 화면의 요구 반영 | 업무별 조회 결과와 캐시를 Service에서 조합 |

Controller–Service–Repository라는 이름만을 DDD의 근거로 삼기보다, 단일 설비에서 출발한 요구가 확대될 때 업무 경계와 책임을 어떻게 다시 정리했는지가 이 사례의 핵심이다.

## 조회 중심 시스템에 맞춘 선택

이 시스템은 설비 데이터를 조회·집계해 제공하는 대시보드다. 모든 조회 DTO를 Entity나 Aggregate로 바꾸기보다 필요한 업무 의미와 규칙을 표현하고, 조회와 집계 흐름을 유지하는 쪽으로 설계했다.

도메인 이벤트, 이벤트 소싱이나 애그리거트 기반 상태 변경을 이 사례의 구현 항목으로 제시하지 않는다. DDD의 모든 전술 패턴을 한꺼번에 적용하는 대신 현재 요구에 필요한 업무 구분과 책임 분리에 집중했다.

## MSA와의 관계

업무별 패키지를 나누는 것과 독립 서비스를 운영하는 것은 다른 결정이다. 이번 작업은 기존 백엔드 내부의 구조를 재정의한 사례이며, 여러 마이크로서비스로 배포 구조를 전환한 사례는 아니다.

설비가 늘어나는 요구에 먼저 대응하고, 서비스의 독립 배포나 데이터 소유권 분리는 별도 설계 판단으로 다룬다.
