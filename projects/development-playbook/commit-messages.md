# [doc] 커밋 메시지 기준

> Conventional Commits 1.0.0 형식을 참고한 제안 규칙이다. 아래 유형 전체가 명세의 필수 항목은 아니다.

## 형식

```text
<type>(<scope>): <변경 내용>

<필요한 경우 변경 이유와 제약>

<관련 이슈 또는 호환성 변경>
```

| 유형 | 사용 목적 |
| --- | --- |
| feat | 기능 추가 |
| fix | 오류 수정 |
| refactor | 의도한 외부 동작을 유지하는 구조 개선 |
| test | 테스트 추가·수정 |
| docs | 문서 변경 |
| build | 빌드·의존성 설정 변경 |
| ci | 자동 검사·배포 파이프라인 변경 |
| chore | 나머지 유지보수 변경 |

`scope`는 `mqtt`, `network`, `order`처럼 영향 영역을 적고 필요 없으면 생략한다. 이 목록은 적용할 팀에서 축소·확장할 수 있다.

## 작성 예시

아래는 작성 방식 설명을 위한 예시이며 실제 수행 이력을 뜻하지 않는다.

```text
fix(network): 본딩 적용 전 중복 NIC 선택 방지

docs(mqtt): 브로커 복구 후 구독 연결 분리 조건 기록

feat(api)!: 응답의 error 필드를 errors 배열로 변경

BREAKING CHANGE: 호출자는 errors 배열에서 오류 목록을 읽어야 한다.
```

## 변경 단위

- 하나의 이유로 설명할 수 있는 변경을 묶는다.
- 테스트와 해당 구현은 함께 추적할 수 있게 둔다.
- `수정`, `작업 중`, `최종`처럼 변경 내용을 알 수 없는 제목은 피한다.
- PR에서 squash 병합을 선택했다면 최종 커밋 제목과 본문을 다시 확인한다.

커밋 메시지만으로 버전이나 릴리스 노트가 자동 생성되지는 않는다. 자동화는 별도 설정이 필요하다.
