- 실행 일자: 2026-10-22 (한국 시간)
- 환경: macOS 15.4, Intel x86_64, Docker Engine 29.4.1, Docker Compose v5.1.3
- 이미지: EMQX 5.0.26, HAProxy 3.0.11-alpine, Mosquitto 클라이언트 2.0.22
- 확인 수단: MQTT 클라이언트 디버그 로그와 EMQX CLI의 클라이언트 목록
- 이번 검증에서 EMQX 웹 콘솔 화면 확인은 수행하지 않았다. 사용자가 수동으로 확인할 절차는 README에 제공한다.

## 관찰 결과

| 항목 | 실제 결과 |
| --- | --- |
| 브로커 독립성 | 각 `cluster status`에 자신만 표시됨 |
| A 공유 구독자 2개, QoS 1 메시지 6개 | A1 4개, A2 2개 수신. 이번 표본에서 총 6개 수신 |
| A 발행 시 B의 같은 이름 공유 구독 | A에서 보낸 6개 메시지를 B에서는 수신하지 않음 |
| B 직접 발행 | B 구독자가 `b-only` 수신 |
| A 중지 후 프록시 구독자 | B에서 동일 클라이언트 ID의 연결 확인. 재구독 후 `after-A-stop` 수신 |
| A 복구 후 새 프록시 발행 | A의 관찰용 구독자가 `after-A-recovery` 수신 |
| A 복구 후 기존 프록시 구독자 | B에 계속 연결되어 위 복구 메시지를 받지 못함 |

단 한 번의 유한한 메시지 표본을 확인한 결과이며 전달 보장, 성능 또는 무중단을 입증하지 않는다. A 복구 후 미수신 판단은 발행 후 2초간 관찰한 로그와 A/B의 클라이언트 목록을 기준으로 했다.

## 확인한 제약과 설정 조정

초기 구성에서는 A 중지 직후 재연결 시 MQTT 연결 응답을 기다리는 지연이 관찰됐다. 최종 구성에서 클라이언트 Keep Alive를 5초, HAProxy client/server 비활성 타임아웃을 15초로 설정한 뒤 전체 절차를 다시 실행했다. [실행 로그](test-output.md)는 이 최종 구성 실행의 기록이다.

A가 복구되어도 B의 기존 연결을 강제로 A로 옮기지 않으므로 새 발행자와 기존 구독자가 분리될 수 있다. 독립 브로커와 단순 백업 지정만으로 서비스 연속성이 확보된다고 판단할 수 없다.

Keepalived, VIP 이동, 호스트 장애, 메시지 유실·중복의 장시간 관찰, 세션 복제 및 운영 규모의 부하 시험은 수행하지 않았다. 과거 구성의 테스트 결과와 이번 재현 결과를 구분한다.
